# CuteGantt

**Gantt charts as code, ready for presentations.**
CuteGantt turns YAML or JSON project plans into SVG Gantt charts. Keep your plans in version control, generate charts from the command line, and compare revisions to show what changed: dates, milestones, progress and scope.

Use it for project roadmaps, proposals, tenders and status reports. Rendering runs locally; your plan does not need to be uploaded to a service.
CuteGantt includes a standalone CLI and a typed JavaScript library that can also run in the browser. It visualizes the schedule you define; it is not an automatic task scheduler.

## Features

- **Text-based plans:** write YAML or JSON with tasks, milestones, groups, owners and progress.
- **SVG output:** generate vector charts for documents, slides and the web.
- **Revision comparisons:** create a diff chart with change notes and Markdown/JSON reports.
- **Flexible timelines:** use calendar dates or time-unit indices, custom units such as sprints, and relative date labels.
- **Presentation controls:** light and dark themes, chart width, font, group summaries and calendar shading.
- **English and Italian output:** localize charts, reports and JSON Schema descriptions.
- **CLI or library:** install a standalone executable without Node.js, or use the browser-safe ESM API in your own application.

## Installation

### macOS and Linux

Install from the latest stable GitHub Release:

```sh
curl -fsSL https://github.com/klinamen/cutegantt/releases/latest/download/install.sh | sh
```

The installer selects the binary for your machine, verifies its SHA-256 checksum and installs it into `~/.local/bin`. No `sudo` or Node.js installation is required. It tests the downloaded executable before replacing an existing installation.

If that directory is not already on your `PATH`, add this to your shell configuration:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

Then check the installation:

```sh
cutegantt --help
```

| Platform | Architectures                  | Notes                                                           |
| -------- | ------------------------------ | --------------------------------------------------------------- |
| macOS    | Intel x64, Apple Silicon ARM64 | Binaries are ad-hoc signed, not notarized.                      |
| Linux    | x64, ARM64                     | Requires glibc; older distributions are not guaranteed to work. |

Windows and Alpine/musl are not supported by the installer. It requires a POSIX shell, curl, tar with gzip support, standard filesystem utilities and either `sha256sum` or `shasum`. Linux detection also uses `getconf`.
To select a version or another installation directory, replace `v1.2.3` with an existing release tag:

```sh
curl -fsSL https://github.com/klinamen/cutegantt/releases/latest/download/install.sh \
  | sh -s -- --version v1.2.3 --dir "$HOME/bin"
```

To inspect the script before running it:

```sh
curl -fsSL -o install.sh https://github.com/klinamen/cutegantt/releases/latest/download/install.sh
less install.sh
sh install.sh
```

Re-run the installer to update. To uninstall a default installation, remove `~/.local/bin/cutegantt`.

The installer downloads the archive and checksum from the same release tag. Download, checksum or runtime errors leave the previous executable intact. Checksums detect corruption but are not independent publisher signatures. Only run an installer you trust.
Release assets are uploaded after the release is published. If the installer or binary is not yet available, wait for the release workflow to finish. You can also download a matching archive and checksum from GitHub Releases, verify the checksum, and extract the executable manually.

### Run From Source

For development or running the CLI with Node.js, use **Node.js 24 or newer**:

```sh
git clone https://github.com/klinamen/cutegantt.git
cd cutegantt
npm ci
npm run build
node packages/cutegantt-cli/dist/cli.js --help
```

To create and install a local CLI package:

```sh
npm run pack:cli
npm install -g ./cutegantt-cli-*.tgz
```

Use the archive generated by `pack:cli`, which bundles the core library. These instructions do not assume that the packages are published to the npm registry.

## Your First Chart

Create `launch.yaml`:

```yaml
project: product-launch
title: Product Launch
subtitle: From discovery to delivery
timeline:
  origin: '2026-10-05'
  timeUnit:
    duration: 1w
    name: Week
tasks:
  - id: discovery
    name: Discovery
    group: Planning
    owner: Product
    start: '2026-10-05'
    end: '2026-10-09'
    progress: 100
  - id: build
    name: Build and integration
    group: Delivery
    owner: Engineering
    start: '2026-10-12'
    end: '2026-10-23'
    progress: 25
  - id: launch
    name: Launch
    group: Delivery
    type: milestone
    date: '2026-10-26'
```

Generate the chart:

```sh
cutegantt launch.yaml
```

The result is `output/launch.svg`. Open it in a browser or use it in an application that supports SVG. With a source checkout, replace `cutegantt` in the examples with `node packages/cutegantt-cli/dist/cli.js`.

Dates use `YYYY-MM-DD`; task end dates are inclusive. Progress ranges from 0 to 100. Give each task or milestone a unique, stable `id` so CuteGantt can match it across revisions. The same plan structure is supported in `.json`, `.yaml` and `.yml` files.
Explore the complete input schema and a larger example:

```sh
cutegantt --schema > gantt.schema.json
cutegantt --schema --lang it > gantt.it.schema.json
```

The repository includes a more detailed plan in [test/fixtures/atlas-2026-09-18.json](test/fixtures/atlas-2026-09-18.json). JSON Schema is the reference for all available fields, including timeline markers, visible ranges and style settings.

## Common Workflows

### Customize a Chart

```sh
cutegantt launch.yaml --theme dark --width 1600 --out-dir charts
cutegantt launch.yaml --group-summary --relative-time --out-dir overview
cutegantt launch.yaml --lang it --out-dir italian
```

Options override the corresponding plan settings. The CLI interface and operational messages are in English; `--lang` selects the language of generated content, not the language of your task names.

Existing output files are protected. Pass `--force` when you intentionally want to overwrite them.

### Compare Revisions

Keep a copy of the original plan, edit the new version, then generate both the current chart and a comparison:

```sh
cp launch.yaml launch-v2.yaml
# Edit dates, progress or tasks in launch-v2.yaml.
cutegantt launch-v2.yaml --previous launch.yaml --mode both
```

The output directory contains:

| File                                                                                                                                                                                                                                                           | Contents                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `launch-v2.svg`                                                                                                                                                                                                                                                | Current plan without comparison annotations |
| `launch-v2.diff.svg`                                                                                                                                                                                                                                           | Chart showing changes against the baseline  |
| `launch-v2.changes.md`                                                                                                                                                                                                                                         | Human-readable change report                |
| `launch-v2.changes.json`                                                                                                                                                                                                                                       | Structured change data                      |
| `launch-v2.notes.svg`                                                                                                                                                                                                                                          | Separate change notes, when generated       |
| Use `--mode diff` for comparison outputs only, or `--notes inline` to place notes within the diff chart. Without `--previous`, CuteGantt looks for the lexical predecessor for the same project; specify the baseline explicitly when reproducibility matters. |

### Show Non-working Days

```sh
cutegantt launch.yaml --shade-weekends --holidays-dir calendars --holiday-labels
```

Holiday calendars are annual JSON or YAML files. Their top-level array is named `holydays` (this spelling is part of the input format), with `start`, `end` and `label` fields for each entry. Shading weekends and holidays is visual only: it does not reschedule tasks.

### CLI Reference

Run `cutegantt --help` for the full option reference.

| Option                                   | Purpose                                                                    |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `--out-dir <directory>`                  | Output directory; defaults to `output`                                     |
| `--mode clean\|diff\|both`               | Rendering mode; defaults to `clean`                                        |
| `--previous <file>`                      | Explicit baseline for a comparison                                         |
| `--theme light\|dark`                    | Override chart colors                                                      |
| `--width <pixels>`                       | Chart width from 1000 to 8000                                              |
| `--font <family>`                        | Override the chart font family                                             |
| `--group-summary` / `--no-group-summary` | Enable or disable group spans and weighted progress                        |
| `--relative-time` / `--no-relative-time` | Switch between relative and absolute date labels                           |
| `--lang en\|it`                          | Language of charts, reports and schema                                     |
| `--notes separate\|inline`               | Placement of change notes; defaults to `separate`                          |
| `--force`                                | Overwrite existing outputs                                                 |
| `--schema`                               | Print JSON Schema; accepts `--lang` but no input file or rendering options |

## Use as a Library

The `cutegantt` core is a typed ESM library for Node.js and browser applications. It exposes plan models, validation, comparison, SVG rendering, Markdown reports and JSON Schema generation without relying on the filesystem or Node.js built-ins at runtime.

```js
import { ProjectPlan, renderSvg } from 'cutegantt';

const plan = ProjectPlan.from({
  project: 'demo',
  title: 'A small project',
  timeline: { origin: '2026-10-05' },
  tasks: [
    {
      id: 'prototype',
      name: 'Build a prototype',
      start: '2026-10-05',
      end: '2026-10-16',
      progress: 40,
    },
  ],
});

const { svg } = renderSvg(plan, { theme: 'light', lang: 'en' });
```

`svg` is a string that your application can save or display. YAML parsing and file handling belong to the CLI; library consumers provide JavaScript objects. See the [public exports](packages/cutegantt/src/index.ts) for the API and its TypeScript types.

To package the library from a checkout, run `npm run build` followed by `npm pack --workspace cutegantt`, then install the generated tarball in your consuming project.

## Development and Contributions

Bug reports, documentation improvements and pull requests are welcome. For a rendering bug, include a minimal plan, the exact command, your platform, and the expected and actual output. Remove confidential project data before sharing examples.

Run commands from the repository root:

```sh
npm ci
npm run build
npm run check
node --test test/gantt.test.mjs test/install.test.mjs
```

`npm run check` runs Prettier, ESLint and TypeScript checks without modifying sources. `npm run format` applies Prettier formatting. Build first on a fresh checkout so the CLI can resolve the core library declarations.

| Path                     | Responsibility                                             |
| ------------------------ | ---------------------------------------------------------- |
| `packages/cutegantt`     | Browser-safe models, validation, comparisons and rendering |
| `packages/cutegantt-cli` | CLI options, YAML/JSON file handling and output files      |
| `scripts`                | Packaging and standalone executable builds                 |
| `test`                   | Regression, browser, packaging, installer and SEA tests    |
| `install.sh`             | Release binary installer for macOS and Linux               |
| Additional checks:       |

```sh
npx playwright install chromium
npm run test:browser
npm run test:pack
npm run test:sea
```

Browser tests require Chromium. Packaging tests use temporary directories and npm's registry or cache. SEA tests build a native executable and need `codesign` on macOS. Installer tests use mocked downloads and isolated directories; they do not install into your home.

`npm test` runs the full suite, including legacy parity tests. Those parity tests currently require the historical implementation and its dependencies in `../../gantt`, outside a standalone clone. Run the focused checks above when that directory is unavailable.

### Build Standalone Binaries

```sh
npm run build:sea
```

The executable is written to `dist/sea/<platform>-<arch>/cutegantt`. The build uses the current Node runtime and is native, not cross-compilation. It bundles the CLI, core library and dependencies into a Node Single Executable Application (SEA).

The [SEA workflow](.github/workflows/sea.yml) builds and tests macOS x64/ARM64 and Linux x64/ARM64. Pushes, pull requests and manual runs produce downloadable Actions artifacts. Publishing a GitHub Release triggers builds for its tag; after all targets pass, the workflow attaches the archives, checksums, build metadata and installer to that release. The tag must include the workflow and installer. Publishing to npm is separate.
